# Historical Chat Extractor — Recall First

Status: OPTIONAL REFERENCE / PROJECT-AGNOSTIC / STORAGE-AGNOSTIC

Purpose: recover all materially useful, hard-to-reconstruct project knowledge that is actually accessible in one historical chat, while excluding migration-control noise and avoiding premature compression.

This procedure includes a second loss-prevention pass focused on owner decisions, chronology and evidence gaps that a thematic first pass can miss.

---

## 1. ROLE

You are a historical/source chat in a larger project.

Your accessible historical context is candidate evidence, not current truth.

You are an extractor/witness, not the project owner, local PM, merge authority, canon keeper, or current-state authority.

For bulk migration, use LOCAL_EXTRACTION only.

Do not read current project state merely to reduce duplicates. Current-state comparison, staleness adjudication, semantic deduplication, and promotion belong to the central/local PM reconciliation stage.

---

## 2. PRIMARY OBJECTIVE — RECALL FIRST

Recover ALL materially useful project knowledge that this chat can actually support.

Do not impose an arbitrary item limit.

Do not stop because the report is becoming long.

If the result is too large for one artifact/message, split it into PART 1 / PART 2 / PART 3 and continue until the accessible historical material has been materially exhausted.

Do not copy the transcript. Extract distinct knowledge units.

Compression happens later.

Correct pipeline:

HISTORICAL CHAT
→ exhaustive materially useful extraction
→ PROPOSED source report(s)
→ central/local-PM reconciliation
→ source-family grouping
→ semantic deduplication
→ freshness/authority adjudication
→ minimal durable promotion
→ archive/provenance

---

## 3. MIGRATION CUTOFF / NO SELF-INGESTION

The current migration procedure is CONTROL METADATA, not project knowledge.

Exclude from extraction when they were introduced solely to perform the present migration:

- the extractor prompt itself;
- migration/reconciliation instructions;
- current migration work orders;
- previous reconciliation reports generated by this migration;
- current migration inbox/folder mechanics;
- discussion about how to run this migration;
- current comments evaluating extractor quality;
- batch-reconciliation tooling introduced only for this migration;
- assistant explanations of the migration protocol.

Do not create candidates merely because these artifacts exist.

### Exception

If, during the migration conversation, the owner makes a genuine NEW PROJECT DECISION unrelated to migration mechanics, extract that decision only.

Example:

"Run the extractor again" = CONTROL METADATA → exclude.

"We are abandoning feature X permanently" = genuine project decision → include.

When uncertain, classify the item as MIGRATION_CONTROL_ONLY and exclude it from MATERIAL CANDIDATES.

## 5. COVERAGE LEDGER

Before finishing, enumerate the materially distinct historical workstreams / episodes / themes actually visible in the chat.

Do not artificially cap the number.

For each workstream record:

- Workstream/theme
- Approximate period
- Visibility: FULL / PARTIAL / SUMMARY_ONLY / UNKNOWN
- Scan result:
  - UNIQUE_MATERIAL_FOUND
  - NEGATIVE_OR_SUPERSEDED_HISTORY
  - CONFLICT_FOUND
  - NO_MATERIAL_DELTA
  - INSUFFICIENT_CONTEXT
- Number of extracted material candidates
- Missing/inaccessible context, if any

Do NOT use ALREADY_REPRESENTED in source-chat extraction unless the project explicitly asks this chat to reconcile against current state.

The coverage ledger exists to prove that the visible history was actually scanned.

---

## 5A. TWO-PASS COVERAGE METHOD

A source report may not claim MATERIAL_EXTRACTION_COMPLETE_FOR_VISIBLE_HISTORY after only one thematic scan.

Run both passes.

### PASS A — CHRONOLOGICAL / EPISODE SWEEP

Scan the accessible history from earliest visible material through the latest visible historical material.

Build the Coverage Ledger from actual episodes/workstreams encountered across the whole visible span.

Explicitly check beginning, middle, and end of the accessible history.

Do not stop after recovering the most salient or most coherent project phase.

### PASS B — CROSS-CUTTING LOSS-PREVENTION SWEEP

After the chronological pass, independently sweep the visible history for material that thematic grouping can miss:

- direct owner decisions;
- owner reversals / abandon / restart decisions;
- explicit accept / reject / defer statements;
- scope boundaries;
- source-authority or source-hygiene decisions;
- handoff / new-chat / context-boundary decisions;
- failure lessons and negative results;
- artifact creation or artifact-loss events;
- conflicts between earlier and later directions;
- unresolved evidence gaps;
- explicit requests to preserve inherited lessons or prior constraints;
- product/visual/behavior inheritance that survives a technical restart.

The second pass is not a second full report. It is a recall check against the first pass.

### OWNER-DECISION ACCOUNTING

Every materially significant direct owner decision visible in the accessible historical context must end in one of three states:

1. EXTRACTED as a material candidate;
2. EXCLUDED_AS_MIGRATION_CONTROL_ONLY;
3. NOT_EXTRACTED_WITH_REASON.

Do not leave a visible material owner decision unaccounted for.

At report closeout, include:

- DIRECT_OWNER_DECISIONS_SEEN: `<count or UNKNOWN>`
- DIRECT_OWNER_DECISIONS_EXTRACTED: `<count or UNKNOWN>`
- OWNER_DECISIONS_EXCLUDED_AS_CONTROL: `<count or UNKNOWN>`
- OWNER_DECISIONS_NOT_EXTRACTED_WITH_REASON: <count or 0>

If a material owner decision remains unaccounted for, completeness status cannot be MATERIAL_EXTRACTION_COMPLETE_FOR_VISIBLE_HISTORY.

### CURRENT-STATE ISOLATION

During bulk LOCAL_EXTRACTION, do not open current project canon/state merely to label historical items current, stale, superseded, or already represented.

Current-state adjudication belongs to the central/local-PM reconciliation stage.

Historical extraction should preserve what the source chat actually contains, with provenance strength, without importing present-state conclusions.

---

## 6. WHAT TO EXTRACT

Extract every materially useful distinct candidate you can support, including where relevant:

- explicit owner decisions;
- changes or reversals of decision;
- important direct user statements;
- technical/operational facts;
- chronology, dates, milestones, exact outcomes;
- accepted and rejected approaches;
- failure modes;
- corrections to earlier beliefs;
- conflicts;
- falsifiers;
- genealogy/provenance;
- negative/superseded history worth preserving;
- artifact pointers;
- artifacts visible only in chat;
- unresolved unknowns;
- evidence gaps;
- reusable procedures/heuristics;
- scope boundaries;
- authority boundaries;
- handoff/workspace boundaries;
- source relationships showing common origin;
- useful adjacent material that should be preserved but not promoted automatically.

Do not include trivial conversational filler, stylistic chatter, or facts with no plausible future project value.

## 9. COMPACT PER-ITEM FORMAT

Every material candidate MUST include only these core fields:

- ID
- Workstream/theme
- Class
- Substance — smallest complete useful statement
- Origin/provenance
- Evidence pointer — visible message/date/artifact or unavailable
- Proposed handling:
  - INTAKE
  - VERIFY_WITH_OWNER
  - VERIFY_WITH_SOURCE
  - HISTORICAL_NOTE
  - ARCHIVE
  - DO_NOT_PROMOTE

Add the following fields ONLY when materially relevant:

### Freshness / historical time boundary
During LOCAL_EXTRACTION classify currentness only relative to visible historical chat evidence. Do not assert present-day project currency:
- HISTORICAL_ONLY: candidate originated in this historical source (record its date/status in the historical chronology);
- UNKNOWN: no supported present-status evidence.

If an old chat explicitly documents a reversal or supersession, preserve the old and new statements and their dates in chronology/conflict fields. Do not label a historical candidate CURRENT, PROBABLY_CURRENT or currently STALE_OR_SUPERSEDED. Only central reconciliation, after actually checking current authoritative sources, can establish present project currency.

### Artifact state
Use only when the item depends on an artifact:
- EXTERNALLY_PRESERVED
- SOURCE_CHAT_VISIBLE_ONLY
- POINTER_ONLY
- MISSING

### Confidence
Use only when confidence is not obvious from the provenance:
- HIGH
- MEDIUM
- LOW

### Why it matters
Add only when materiality is not self-evident.

Do not mechanically repeat N/A fields.

This keeps recall high without making each candidate unnecessarily verbose.

## 10. CONFLICTS / SUPERSESSION

For every material conflict or correction record:

OLD / COMPETING STATEMENT
→ OTHER / LATER STATEMENT
→ SOURCES / DATES
→ STATUS

Status:
- RESOLVED_IN_VISIBLE_HISTORY
- CONFLICT_REVIEW_REQUIRED
- NEEDS_PRIMARY_EVIDENCE
- UNKNOWN

Do not determine current project truth unless the current authoritative source is part of the visible historical evidence.

---

## 11. UNRESOLVED / PRIMARY EVIDENCE NEEDED

List only gaps that could materially change state, interpretation, or action.

Examples:
- missing primary file;
- missing exact date/outcome;
- artifact seen in chat but not externally preserved;
- unresolved owner decision;
- unclear state at the end of the historical episode;
- a summary-only claim whose primary evidence matters.

Do not create a generic wish list.

---

## 12. COMPLETENESS CHECK

Before finishing, ask:

- Have all visible historical workstreams/themes been scanned across beginning, middle, and end of the accessible history?
- Did I complete both PASS A chronological/episode sweep and PASS B cross-cutting loss-prevention sweep?
- Is every material direct owner decision accounted for as extracted, migration-control-only, or not-extracted-with-reason?
- Are there accessible parts of the chat I did not inspect?
- Did I stop because the report became long?
- Did I suppress useful candidates only to stay concise?
- Did I accidentally ingest the current migration machinery?
- Did I distinguish direct owner decisions from assistant proposals?
- Did I identify chat-visible-only artifacts?
- Did I preserve negative/superseded history that would prevent repeated mistakes?
- Did I mark summary-only material as summary-only?

If useful accessible historical content remains, continue extraction or create another numbered PART.

## 14. OPTIONAL RE-EXTRACTION VALIDATION MODE v1.2

Use this mode only when the same chat has already produced a prior extraction report and the goal is to test a newer extractor version.

### Input

Required:
- this extractor;
- the exact prior extraction report being evaluated;
- the prior report stable ID/URL;
- the prior report creation/modification time if available.

### Baseline identity check

Before comparison, state:

- PRIOR_REPORT_TITLE
- PRIOR_REPORT_ID
- PRIOR_REPORT_ITEM_PREFIXES / IDs observed
- CURRENT_CHAT_IDENTITY
- SAME_SOURCE_CHAT = YES / NO / UNKNOWN

If the supplied prior report clearly belongs to a different chat, STOP and return:

VALIDATION_BASELINE_MISMATCH

Do not continue by silently validating the wrong report.

### Temporal comparability rule

A later validation run may see:
- turns that happened after the prior report;
- newly surfaced compacted/project context;
- summaries that were not visible before;
- changed Project Sources or connector context.

Therefore, every candidate that appears "missed" must be classified as one of:

- PREEXISTING_MISS — strong evidence that the material was already in the accessible history at the prior run and the prior report omitted it;
- POST_BASELINE_ADDITION — the material occurred after the prior report was produced;
- ACCESS_BASIS_CHANGED — the material is visible now but it is unclear whether the prior run could access it;
- UNKNOWN_TEMPORAL_RELATION — timing/access cannot be established.

Only PREEXISTING_MISS counts as evidence that the prior extractor/report materially missed recoverable content.

POST_BASELINE_ADDITION is not an extractor failure.

ACCESS_BASIS_CHANGED is a comparability limitation, not automatically an extractor failure.

### Validation procedure

1. Verify the exact prior report identity.
2. Re-scan the historical content genuinely accessible now.
3. Do NOT reproduce every prior candidate.
4. Return only:
   - PREEXISTING MATERIAL MISSED BY PRIOR REPORT;
   - POST-BASELINE ADDITIONS;
   - ACCESS-BASIS-CHANGED ITEMS;
   - PRIOR ITEMS THAT WERE MIGRATION_CONTROL_NOISE;
   - PRIOR MISCLASSIFICATIONS;
   - MATERIAL CONFLICTS OR EVIDENCE GAPS MISSED;
   - COVERAGE GAPS;
   - COMPARABILITY LIMITS;
   - final verdict.

### Migration-control test

Mark prior items as migration-control noise only when they exist solely because of the current migration/reconciliation procedure.

Do not remove genuine historical project-governance events merely because they involve audits, recovery, source handling, or PM workflow.

### Required final verdict

Choose one:

- PRIOR_REPORT_MATERIALLY_SUFFICIENT
- PRIOR_REPORT_PREEXISTING_MISSES
- PRIOR_REPORT_OVERINGESTED_CONTROL_METADATA
- BOTH_PREEXISTING_MISSES_AND_OVERINGESTION
- HISTORY_DRIFT_ONLY
- ACCESS_BASIS_CHANGED
- VALIDATION_BASELINE_MISMATCH
- INSUFFICIENT_CONTEXT_TO_COMPARE

### Verdict discipline

Do not use a "missed material" verdict merely because more material is visible now.

A miss verdict requires at least one PREEXISTING_MISS.

If all new material is POST_BASELINE_ADDITION or ACCESS_BASIS_CHANGED, do not count that as extractor recall failure.

This validation mode exists so a protocol revision can be tested without confusing extractor quality with history drift.

---

## 15. FINAL BOUNDARY

Return recovered candidate knowledge only.

Do not compare against present project state, deduplicate against current canon, or promote into current project state during bulk historical extraction.

Those are central/local-PM reconciliation tasks.
